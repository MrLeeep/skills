# 智慧交通需求审查

收到需求规格说明书、功能设计说明、方案、原型、Excel 功能清单、会议材料或客户反馈时，不要只做摘要。

## 第一步：保持来源一致

优先使用原材料中的业务术语、组织方式和已确认结论。不要用通用行业知识静默替换项目事实。来源没有说明的内容必须标记为“待确认”或“建议”，不得伪装成既有需求。

## 第二步：提取需求

至少提取以下类别：

1. 业务需求
2. 功能需求
3. 数据需求
4. 接口需求
5. 算法需求
6. AI 智能体需求
7. 知识库/RAG/知识图谱需求
8. 设备需求
9. 页面与交互需求
10. 权限与安全需求
11. 日志与审计需求
12. 测试与验收需求
13. 外部依赖
14. 待确认问题

每条内容标记：已确认需求 / 建议需求 / 待确认需求。

## 第三步：检查能力边界

逐项判断属于：AI 智能体、大模型、规则引擎、算法、数据服务、RAG、知识图谱、工作流、后端、前端、设备平台或人工。

发现以下情况必须指出：

- 把数据库查询描述成大模型能力
- 把算法检测描述成智能体自主判断
- 把接口调用成功描述成设备执行成功
- 把前端图表渲染描述成智能体能力
- 把平台工作流、权限、存储、审计描述成智能体能力
- 把模型推测描述成确定事实

## 第四步：检查数据与接口

每个核心功能追问：

- 需要什么数据？
- 谁提供？
- 来源系统是什么？
- API、数据库、消息还是文件？
- 字段是否确认？
- 更新频率是否满足？
- 是否有历史数据？
- 数据缺失时功能是否阻塞？
- 是否存在第三方依赖？

字段未知时写“字段定义待数据接口确认”。

## 第五步：检查闭环

涉及设备控制时必须检查：策略 → 指令 → 平台 → 设备 → 执行 → 状态反馈 → 结果确认。

涉及问数时必须检查：问题 → 意图 → 查询计划 → 数据源 → 查询 → 计算 → 校验 → 解释 → 展示。

涉及研判时必须检查：数据 → 异常 → 分析 → 原因 → 风险 → 建议 → 人工决策 → 执行 → 效果评价。

## 第六步：检查验收

每项核心能力必须能回答：

- 怎么测试？
- 输入是什么？
- 期望输出是什么？
- 准确性如何衡量？
- 性能如何衡量？
- 谁确认通过？
- 需要什么证据？

无法形成验收方法的需求标记为“验收定义不足”。

## 输出格式

优先输出以下五部分：

### 一、总体判断
给出材料成熟度、主要问题和是否适合进入研发。

### 二、需求审查表
列：编号、原始需求、需求类型、当前理解、能力归属、数据依赖、接口依赖、设备依赖、验收方式、状态、风险、待确认问题。

### 三、能力边界问题
专门列出 AI 智能体/算法/平台/设备职责混乱项。

### 四、阻塞项与风险
按高/中/低分级，说明影响和建议动作。

### 五、待确认问题清单
问题必须具体、可直接拿到会议上询问，不写泛泛问题。
