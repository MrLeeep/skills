# 智慧交通功能清单生成

不要把需求原文简单复制到 Excel。目标是把需求拆到能够开发、联调和验收的粒度。

## 拆解层级

业务域 → 一级模块 → 二级模块 → 三级功能 → 业务场景 → 功能逻辑

## 每项功能至少包含

- 功能编号
- 一级模块
- 二级模块
- 三级功能
- 功能名称
- 需求来源
- 业务场景
- 用户角色
- 触发条件
- 前置条件
- 输入
- 数据来源
- 处理逻辑
- 业务规则
- 算法依赖
- AI 智能体依赖
- 知识库/RAG/知识图谱依赖
- 接口依赖
- 设备依赖
- 输出
- 页面交互
- 审核机制
- 异常处理
- 执行反馈
- 验收标准
- 优先级
- 当前状态
- Owner
- 待确认问题

## 粒度判断

一条功能只有在以下角色都能理解时才算拆解完成：

- 产品知道页面和交互怎么设计
- 后端知道输入、处理和接口
- 算法知道输入输出和指标
- Agent 研发知道工具、规则和边界
- 测试知道怎么写测试用例
- 项目经理知道依赖、Owner 和风险
- 甲方知道最终会交付什么

## 智慧隧道建议业务域

- 应急处置 / 预案自动生成
- 数字问数 / 数据服务
- 运营管理综合研判
- 设备运维
- 能耗管理
- 通行效率
- 安全风险
- 供配电保障
- 隧道机电联动

不要自行添加项目材料没有提出的功能；行业通用但材料未确认的内容标记为“建议需求”。

## 验收标准写法

禁止写“功能正常”“满足需求”等不可测试表述。优先写成：

给定前置条件 + 输入/操作 + 系统行为 + 期望结果 + 可验证证据。

## 输出格式

### 默认正式成果：Excel

凡用户要求“功能清单”“软件功能清单”“需求功能清单”“功能底账”等结构化清单，默认优先生成 `.xlsx` 文件，不要只输出 Markdown 表格。

除非用户明确指定其他格式，Excel 作为正式版本；Markdown 仅作为可选预览或说明材料。

推荐工作簿至少包含：

1. `软件功能清单`：完整功能底账，每行一个可独立识别、开发、测试或验收的功能项
2. `公共能力清单`：统一认证、组织权限、数据服务、日志审计、规则引擎、大模型服务、智能体框架、RAG、知识库、接口服务、设备接入等可复用能力
3. `待确认功能`：影响范围、详细设计、开发或验收的待确认项
4. `需求追溯矩阵`：需求来源 → 功能编号 → 功能项 → 验收要求
5. `统计汇总`：按模块、需求状态、建设属性等维度汇总

Excel 应具备基本可用性：表头清晰、冻结首行、启用筛选、合理列宽、自动换行；需要长期维护的枚举字段可设置数据验证下拉选项。不要为了视觉效果大量合并单元格，避免影响筛选、排序和后续报价测算。

如果用户已有甲方或公司模板，优先沿用该模板，不另造格式。

### Markdown 使用场景

只有以下情况可优先使用 Markdown：

- 用户明确只要文本预览
- 当前任务只是讨论功能拆解思路
- 无需生成正式文件

即使同时生成 Markdown，只要任务目标是正式功能清单，仍应以 `.xlsx` 为主文件。

## 强制规则

1. 功能清单正式交付默认优先 `.xlsx`
2. 不得因为输出 Excel 就机械拆分功能数量
3. 不得虚构需求、接口、字段、算法、设备能力或审批关系
4. 未确认内容必须标记待确认
5. 功能清单必须能继续用于详细设计、研发排期、测试验收和工程量梳理
