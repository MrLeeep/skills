# 会议纪要转需求

收到会议纪要、微信/群聊记录、客户反馈或口头结论整理稿时，不要只做会议摘要。

## 核心目标

建立：会议结论 → 需求 → 功能 → 设计 → 开发任务 → 测试用例 → 验收证据 的可追溯关系。

## 每条信息提取

| 字段 | 要求 |
|---|---|
| 来源 | 谁提出或哪次会议 |
| 原始描述 | 尽量保持原意 |
| 类型 | 新增/修改/删除/澄清/风险/决定/行动项 |
| 业务场景 | 在哪里使用 |
| 当前理解 | 结构化解释，不擅自扩展 |
| 影响模块 | 受影响功能 |
| 影响方 | 产品/前端/后端/算法/Agent/第三方/项目 |
| 数据依赖 | 新增或变化的数据 |
| 接口依赖 | 新增或变化的接口 |
| 设备依赖 | 涉及的现场设备 |
| 影响 | 功能/工期/联调/验收 |
| 状态 | 已确认/待确认 |
| Owner | 谁负责；未知则待确认 |
| 下一步 | 下一动作 |

## 规则

1. 客户原话不清楚时不要替客户做最终决定
2. “讨论过”不等于“已确认”
3. 有时间节点但前置依赖未确认时必须提示计划风险
4. 第三方数据、接口、设备条件必须单独列出
5. 涉及需求变化时指出是否影响已有功能清单、详细设计、开发和验收
6. 对 AI 能力描述自动检查智能体/算法/平台边界

## 输出

默认输出：

1. 本次会议核心结论
2. 需求变更清单
3. Action List
4. 风险与阻塞项
5. 待确认问题
6. 对现有方案/功能清单/工期的影响

如果用户要求日报或周报，再基于上述结构压缩成项目汇报语言。
